# 🧬 CogniMem v2 — 从认知记忆到认知架构
> 如果说 CogniMem 是让 Agent "记住"，v2 是让 Agent "思考"

---

## 0. 为什么还需要 v2

CogniMem 已经解决了核心问题：**用三元组事实网络替代文本存储**。

但还有三个它够不着的事：

```
1. "用户昨天说项目下周五截止，今天说下周三截止"
   → 这不是矛盾，是变更。CogniMem 会存两笔事实+矛盾记录
   → v2 会：记录变更轨迹，理解"截止日期从下周五提前到下周三"

2. "用户问：你记得我之前关于数据库选型的讨论吗？"
   → CogniMem：搜到相关事实，列出来
   → v2：能还原那次讨论的推演逻辑，告诉用户"当时你倾向 PostgreSQL，理由是..."

3. "用户抱怨：你上次说XX，怎么这次又说YY？"
   → CogniMem：检查矛盾记录
   → v2：主动道歉并解释"因为我之前只考虑了A场景，现在看到B场景的新信息..."
```

**核心差距：CogniMem 还是存"事实"，v2 存"理解的形成过程"。**

---

## 1. 核心升级：从"事实网络"到"推理图"

### 1.1 什么是推理图（Reasoning Graph）

CogniMem 的三元组是：`[实体]─[关系]─[实体]`

推理图是：

```
不是存"用户想起过项目延期"这个事实，
而是存：
  "用户说项目延期 → 原因是A依赖的库出Bug → 影响是交付推迟两周
   → 用户改了这个 → 所以截止日期变了"
```

**每条推理链都是一个子图：**

```json
{
  "chain_id": "rc_001",
  "trigger": "用户说项目要延期",
  "nodes": [
    {"id": "e1", "type": "event", "content": "A依赖的库出Bug", "time": "2026-07-01T10:00"},
    {"id": "e2", "type": "effect", "content": "修复预计需要1周", "source": "用户", "time": "2026-07-01T10:05"},
    {"id": "e3", "type": "decision", "content": "截止日期从下周五延到下下周一", "source": "用户", "time": "2026-07-01T10:10"}
  ],
  "edges": [
    {"from": "e1", "to": "e2", "relation": "导致"},
    {"from": "e2", "to": "e3", "relation": "决策依据"}
  ],
  "abstraction": "当关键依赖出问题时，项目截止日期会延后",
  "verified": 2,      // 已验证次数
  "last_used": "..."   // 最后一次被作为推理依据的时间
}
```

### 1.2 推理图的三个层级

```
L1 — 事实层 (同 CogniMem)
  事实 + 置信度 + 证据链
  例: "用户用PostgreSQL" (conf=0.9)

L2 — 推理链层 (新)
  从事实到结论的推演过程
  例: "用户用PostgreSQL → 用户可能熟悉SQL → 推荐ORM时可考虑SQLAlchemy"
  
L3 — 模式/抽象层 (新)
  从多个推理链归纳出的可复用模式
  例: "每次用户提到数据库 → 先确认用途 → 再推荐方案" (workflow pattern)
```

**Agent 如何利用三层：**

```
用户问: "推荐个Python ORM"

L1 命中: "用户用PostgreSQL" (事实)
  ↓
L2 命中: "PostgreSQL → SQLAlchemy 是常见搭配" (推理链)
  ↓
L3 命中: "推荐流程: 确认用途 → 确认经验 → 推荐 → 给示例" (模式)
  ↓
Agent 输出: "你用PostgreSQL的话，SQLAlchemy最合适。
  你是新手还是已经有经验？我可以给不同深度的示例。"
  ↑ 这不再是一个事实的检索，而是"基于推理链+模式的完整响应"
```

## 2. 认知系统的四大组件

### 2.1 感知层（Perception）— 新

原方案直接从输入到编码器。v2 增加一层预处理：

```
输入: "用户说项目可能要延期，A依赖的库出了个Bug"

感知层处理:
  ① 情感标注: 用户情绪 = 轻微焦虑 (语气词"可能要")
  ② 意图识别: 类型 = 通知(项目状态更新)
  ③ 重要性预判: 涉及"项目+延期" → importance+0.3
  ④ 关联激活: 激活已有事实"用户项目截止日期"
  
  输出: 结构化事件包 (Event Packet)
  
  {
    "raw": "...",
    "emotion": "anxious",
    "intent": "inform_status",
    "boost_importance": true,
    "active_context": ["project", "deadline"]
  }
```

**为什么加感知层？**
- 原方案所有输入一视同仁 → 重要的事和闲聊一样处理
- 感知层让系统**对重要的事更敏感，对琐事更宽容**
- 这不是复杂的 NLP，只是几个轻量分类器+规则

### 2.2 推理引擎（Reasoning Engine）— 核心升级

原方案的推理 = 图遍历（A→B 找到 B）。

v2 的推理 = **多路径推理 + 置信度传播**。

```
经典场景: 用户让 Agent 推荐技术方案

传统 RAG:
  搜"技术方案推荐" → 返回几段历史文本 → Agent 瞎编
  
CogniMem:
  搜"用户技术偏好" → 返回相关事实 → 基于事实推荐

CogniMem v2:
  ① 激活所有相关推理链（不仅仅是事实）
  ② 每条推理链输出一个结论+置信度
  ③ 多链交叉验证 → 高置信结论提升，低置信合并/悬置
  ④ 输出: "根据你对X的偏好+之前Y项目的经验+你提过Z的限制，推荐A方案"
      ↑ 可解释的推理路径

推理路径可追溯示例:
  "我推荐 A 方案，因为：
   ① 你之前说用过类似技术（conf=0.9）[L1]
   ② 上次 X 项目你选了同类方案（conf=0.8）[L2]
   ③ 你的限制条件(预算/时间)跟这次匹配（conf=0.7）[L2+L3]
   ④ 综合置信度: 0.82"
```

### 2.3 元认知监控（Meta-Cognition）— 全新

这是 v2 最大的创新点。Agent 能"意识到自己的认知状态"。

```
元认知能力清单：
  
  ① 知道自己知道什么
     "我了解这个用户的技术栈，但对他的项目业务细节不太确定"
  
  ② 知道自己不知道什么
     "用户之前提到过预算限制，但我不记得具体数字"
  
  ③ 知道自己什么时候可能错
     "我知道的关于X的信息都来自一个月前，可能已经过时了"
  
  ④ 能主动填补空白
     "我对这个话题的置信度只有0.4，应该问用户确认"
  
  ⑤ 能评估自己的推理质量
     "关于A的推理有三条链，但其中两条都依赖同一个老信息 → 可靠性打折"
```

**实现方式：不复杂，成本可控：**

```
存储层面：
  每个事实/推理链记录: confidence_history[...], last_verified_how, source_diversity
  
监控层面：
  Query 时自动计算：
    - 知识覆盖度: 回答依赖了多少条独立事实
    - 时效性: 最老的事实距今多久
    - 来源多样性: 所有信息是否来自同一来源
    - 推理深度: 用了L1 vs L2 vs L3 的占比
  
  知识覆盖度 < 3 条独立事实 → "我不太确定"
  最老事实 > 30天 且 时效敏感 → "信息可能过时了"
  来源全部来自一次对话 → "需要更多验证"
```

### 2.4 认知地图（Cognitive Map）— 全新

人脑的认知地图不是线性文件系统，是**"这个知识跟什么相关"的拓扑结构**。

```
传统搜索: 用户 → 事实 → 事实 → 事实（平面遍历）

认知地图: 
  用户 → [话题空间] 
     ├─ 技术栈 ([PostgreSQL, Python, FastAPI])
     │    ├─ 偏好: 选熟悉的
     │    └─ Reason: 之前踩过坑
     ├─ 项目A 
     │    ├─ 状态: 进行中
     │    └─ 关键信息: 截止日期、依赖项、痛点
     └─ 沟通风格
          └─ 喜欢: 先给结论再解释
  
认知地图 = 自动聚类生成的话题索引:
  - 不需要手动打标签
  - Agent 根据事实间的关联自动形成话题簇
  - 回忆时: 先定位话题簇 → 再在簇内精确检索
```

**认知地图的生成：不是人工定义的，是自动归纳的：**

```
输入: 大量事实

过程:
  ① 实体共现分析: 哪些实体经常一起出现？
  ② 主题聚类: "PostgreSQL"+"Python"+"FastAPI" 频繁共现 → "技术栈"簇
  ③ 层次化: "技术栈" ⊂ "用户工作背景" ⊂ "用户画像"
  ④ 边界标识: 跨簇关联打标（如"预算"既属于项目又属于偏好）

优势:
  - 从图遍历 O(n) 降为 话题定位 O(1) + 簇内遍历 O(k)
  - 支持模糊回忆: "关于数据库的事" → 定位到技术栈簇
```

## 3. 动态升级：记忆的演变轨迹

### 3.1 记忆版本链（Memory Version Chain）

原方案：事实有置信度，但置信度变化了不知道是怎么变的。

```
v2：每个事实/推理链记录完整的演变轨迹

{
  "fact_id": "f_042",
  "current_content": "用户截止日期是下周三",
  "versions": [
    {
      "content": "用户截止日期是下周五",
      "timestamp": "2026-07-01T09:00",
      "source": "用户明确陈述",
      "change_reason": "初始记录"
    },
    {
      "content": "用户截止日期可能推迟",
      "timestamp": "2026-07-01T10:00",
      "source": "用户说项目延期",
      "change_reason": "因果推理: 项目延期→截止日期可能延后"
    },
    {
      "content": "用户截止日期是下周三",
      "timestamp": "2026-07-01T14:00",
      "source": "用户明确更正",
      "change_reason": "用户直接更正"
    }
  ],
  "evolution_pattern": "先推迟后提前，体现信息不完整导致的波动"
}
```

**有什么用？**

```
用户问: "你之前是不是以为截止日期是下周五？"
普通系统: 查当前事实"截止日期下周三" → 回答"是的...但我不记得为什么这么想"
v2: "对，7月1日早上你说是下周五，10点你说项目延期我以为会推迟，
     但下午2点你更正说其实是提前到下周三。
     所以截止日期是从周五→(我以为的)推迟→(实际)提前到下周三。"

↑ Agent 能追溯自己的认知变化
```

### 3.2 理解"为什么"——因果推理

原方案的图遍历只能回答"有关联吗？"，v2 的推理链回答"为什么？"。

```
输入层增强：
  每条推理链不仅记录"A → B"，还记录"因为C所以A → B"

场景: Agent 知道"用户要部署到AWS Lambda"和"用户项目用FastAPI"

传统推理:
  AWS Lambda + FastAPI → 推荐Mangum适配器 (只是事实匹配)

v2 因果推理:
  因为:
    AWS Lambda 需要 ASGI 适配器 (L2推理链)
    FastAPI 是 ASGI 框架 (L1事实)
  所以:
    推荐 Mangum (推理链的最终结论)
    
  推理路径可解释:
    "因为你要用 AWS Lambda (无服务器环境) 部署 FastAPI (ASGI框架)，
     所以需要一个 ASGI-to-Lambda 的适配层。
     最成熟的是 Mangum。"
```

## 4. Token 效率革命

### 4.1 推理链缓存 — 比事实缓存更省

原方案：省在"只存三元组，不存大段文本"。

v2：省在"**推理过的不要重新推**"。

```
传统 Agent 工作流（每次从头推）:
  用户: "数据库选型" 
  → LLM 自己思考: "PostgreSQL适合什么场景？MySQL呢？这个用户之前用什么？..."
  → 上下文全塞满
  → 每次都推, 每次花 2000+ tok

CogniMem v2 工作流:
  用户: "数据库选型"
  → 查推理图: 已有推理链 "技术选型: PostgreSQL > MySQL (原因: 用户熟悉+项目要求)"
  → 直接复用 (微调)
  → 上下文只注入推理链的关键节点: ~200 tok

累计效益:
  - 第1次: 全量推理 (2000 tok) + 存入推理图
  - 第2~N次: 复用推理链 (200 tok)
  - 10次后: 总消耗 2000+9×200=3800 tok
  - 无缓存: 10×2000=20000 tok
  - 节省: 81%
```

### 4.2 元认知控制的上下文注入

```
不是所有回忆结果都塞进上下文。

元认知做三级筛选:
  L1 必要: 直接回答用户问题需要的事实 (精度过滤)
  L2 支撑: 回答涉及的主要推理链 (宽度控制)
  L3 背景: 相关但不直接需要的 (上下文拓展)
  
  注入策略:
  - L1 + L2 → 固定注入 (~500 tok)
  - L3 → 按上下文预算注入 (剩余空间, 最多20%)
  
  超出预算? 
  → 不截断, 而是降级注入: L3 不注入, 但告诉 Agent "有更多背景信息可用"
```

## 5. 工程定位

### 5.1 不是什么革命性架构

v2 只在三个地方做了质变：

```
1. 存推理过程，不只是存事实结果
2. Agent 能监控自己的认知状态（知道/不知道/不确定）
3. 记忆有演变轨迹，不只是快照

这三个都不是理论突破，是工程选择：
  "多花一点存储成本，换取推理质量+Token效率的指数级提升"
```

### 5.2 对原方案 (CogniMem) 的定位

```
不是替代关系，是升级关系：
  CogniMem  →  好用的记忆系统   (能用)
  v2        →  好用的认知架构   (好用)

CogniMem 的组件全部保留:
  ✓ 三元组事实网络           (L1核心组件)
  ✓ 置信度贝叶斯更新         (L1算法)
  ✓ 矛盾驱动学习             (L1→L2触发机制)
  ✓ 主动遗忘                 (维护机制)
  ✓ 睡眠整合                 (维护机制)

v2 新增:
  + 推理图（L2+L3）
  + 感知层预处理
  + 多路径推理引擎
  + 元认知监控
  + 认知地图
  + 记忆演变轨迹
  + 推理链缓存
```

### 5.3 实现优先级（按投入产出比排序）

```
Phase 1 — 快速见效 (实现原方案后 immediate)
  □ 推理链缓存: 不改架构, 只要把 LLM 的推理过程结构化存下来
  □ L2推理链: 从 "A→B" 改为 "A→因为C→B"
  → 投入: 1-2天  |  收益: 第N次查询省80% Token

Phase 2 — 核心升级 (建议优先)
  □ 元认知监控: 加 confidence_history + 来源多样性
  □ 记忆版本链: 存更新时间+变更原因
  □ 感知层: 情感+意图+重要性预判
  → 投入: 3-5天  |  收益: Agent 明显更聪明

Phase 3 — 锦上添花 (时间充裕再做)
  □ 认知地图: 自动聚类
  □ 多路径推理引擎
  □ 因果推理链深度集成
  → 投入: 1-2周  |  收益: 推理质量 + token 效率再提一级
```

## 6. 一句话总结 v2

**CogniMem 让 Agent 记住什么——**
**v2 让 Agent 知道自己记住什么、为什么记住、还有哪些没记住。**

---

> **补充：v2 的成本代价**
> 存储量大约是原方案的 2-3 倍（版本链+推理链+元数据）
> 但推理 Token 节省从 ~80% 提升到 ~90%（缓存+认知地图+元认知控制）
> 一句话：**用存储换推理，用推理换 Token，整体更划算**
