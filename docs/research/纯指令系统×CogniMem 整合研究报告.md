## 一、方案定位

### 一句话定义

> **一个会自己长大的执行系统。**
> **AI 做新事、纯指令做旧事、CogniMem 记住所有事——旧事做多了就变模块，AI 就越来越闲。**

### 三者的关系

```
AI 大模型（花几分钱）
  │
  ├── 处理"还没模块"的新需求（爬数据、分析、转换……）
  ├── 处理完 → 结果写入 CogniMem
  └── 系统判断：这个操作以后还会不会做？
        │
        ├── 会 → 沉淀成模块 → 下次拖拽免费执行
        └── 不会 → AI 干一次完事

纯指令执行（零成本）
  │
  ├── 已经有模块的 → 拖拽/命令执行，毫秒级
  ├── 执行结果自动写入 CogniMem
  └── 跑越多，记忆越丰富，推荐越准

CogniMem 记忆（桥梁）
  │
  ├── 记录"哪个模块什么时候跑了、结果如何"
  ├── 记录"AI 处理过什么类型的任务、频次多高"
  ├── 记录"故障模式+解决方案"
  └── 当某个 AI 任务频次够了 → 自动提醒"该做模块了"
```

## 二、CogniMem 去 LLM 后的骨架

### 去掉的（3 项）

| 原功能 | 依赖 LLM | 去掉原因 |
|--------|---------|---------|
| 三元组提取（自然语言→结构化） | ✅ | 纯指令系统不需要——数据本身就是结构化键值对 |
| 抽象归纳（碎片→高层知识） | ✅ | 退化，模块的目录组织和标签就是天然分类 |
| 主动学习（生成追问） | ✅ | 执行系统不需要主动学，需要"用过的记下来" |

### 保留的（不需要 LLM 的全部保留）

```
CogniMem 核心骨架（所有计算纯本地、纯数学）
│
├── 三元组存储引擎
│   ├── PostgreSQL/SQLite 持久化
│   ├── L0/L1/L2 三级缓存（L0 内存 1ms / L1 SQLite 10ms / L2 DB 50ms）
│   └── 版本链（每次变更记录原因+新旧值）
│
├── 置信度系统
│   ├── 初始置信度（首次记录赋予基线值）
│   ├── 确认提升（同一条数据多次确认 → 置信度+）
│   └── 矛盾降权（矛盾冲突 → 置信度-）
│
├── 艾宾浩斯遗忘曲线
│   ├── 半衰期：抽象 60 天 / 高置信 30 天 / 普通 14 天 / 低置信 7 天
│   ├── 访问修正：常访问的衰减更慢
│   └── 核心数据永不衰减
│
├── 上下文感知召回
│   ├── 评分 = 置信度(50%) + 重要性(20%) + 新鲜度(20%) + 相关度(10%)
│   └── 每次查询返回排序后的最相关结果
│
├── 知识图谱引擎
│   ├── 节点：模块 / 用户 / 标签 / 故障模式
│   ├── 边：依赖 / 组合 / 替代 / 报错 / 解决方案
│   └── 可视化图谱（Web 页面）
│
└── Web UI 层
    ├── 模块面板（拖拽执行区）
    ├── AI 任务记录面板（显示即将可沉淀的操作）
    ├── 图谱页（模块关系可视化）
    └── 仪表盘（系统状态 + 记忆统计 + 沉淀率）
```

**整个骨架 = 纯数据结构的增删改查 + 数学公式计算。不需要 GPU、不需要模型文件、不需要调用任何外部 API。**

## 三、三合一模式：AI + 纯指令 + CogniMem

### 3.1 核心执行流程

```
用户来了一个需求
        │
        ▼
  ┌─────────────────────────────┐
  │  第一步：查有没有现成模块     │
  │                             │
  │  查模块目录 → 匹配 NLU 意图  │
  │  → 查 CogniMem 历史记录     │
  └─────────────┬───────────────┘
                │
        ┌───────┴───────┐
        ▼               ▼
    有现成模块         没有现成模块
        │               │
        ▼               ▼
  拖拽执行            走 AI 大模型
  毫秒级              临时处理
  零成本              花几分钱
        │               │
        ▼               ▼
  结果写入           结果写入
  CogniMem          CogniMem
                        │
                        ▼
              ┌─────────────────────┐
              │  第二步：判断沉淀     │
              │                     │
              │  CogniMem 自动统计： │
              │  这个类型的操作       │
              │  出现过几次了？      │
              └──────────┬──────────┘
                        │
                ┌───────┴───────┐
                ▼               ▼
            频次够了         频次不够/一次性
                │               │
                ▼               ▼
        建议做成模块        留在记忆里
        你花 30 分钟写      下次再触发 AI
        以后免费执行        频次上去了再沉淀
```

### 3.2 沉淀率——这个方案的核心指标

```
沉淀率 = 经过 AI 处理后转化为模块的比例

    沉淀率 0%：每次用完 AI 就算，跟直接用 ChatGPT 没区别
    沉淀率 30%：不错，AI 费用在下降
    沉淀率 60%：很好，大部分常用操作已经免费了
    沉淀率 80%+：AI 只处理全新需求，费用降到忽略不计
```

**CogniMem 专门为"提高沉淀率"服务：**

```
不是"你拍脑袋决定什么该沉淀"，
是 CogniMem 自动告诉你：这个操作已经出现了 N 次，
同类操作出现了 M 次，建议沉淀。
```

### 3.3 时间维度上的效果

```
第一周：
  AI 处理：    90% 的任务
  模块处理：   10% 的任务
  沉淀率：     还在积累中
  AI 费用：    🔴 最高
  用户体感：   AI 啥都能干

第三个月：
  AI 处理：    40% 的任务（全新需求）
  模块处理：   60% 的任务（已沉淀为模块）
  沉淀率：     ~50%
  AI 费用：    🟡 降了 50%+
  用户体感：   常用操作秒出，新需求等几秒

第六个月：
  AI 处理：    15% 的任务
  模块处理：   85% 的任务
  沉淀率：     ~75%
  AI 费用：    🟢 忽略不计
  用户体感：   几乎所有日常操作都是拖拽秒出
```

### 3.4 隐藏价值：AI 任务也在喂 CogniMem

AI 不只是干活——它还在帮系统理解用户的表达方式：

```
用户对 AI 说："帮我爬一下这个网页的竞品价格"
AI 临时跑脚本抓了数据返回

CogniMem 自动记录：
  "用户 要求 爬竞品价格"          ← 意图
  "操作类型 网页数据抓取"          ← 分类
  "结果结构 表格数据"              ← 输出格式
  "触发次数 3"                    ← 频次

下次另一个用户说："帮我看看对手多少钱"
CogniMem 发现这个意图跟"爬竞品价格"相似度 89%
→ 推荐直接用已有模块，或微调一下就行
→ 甚至不需要重新调 AI
```

**AI 做得越多，CogniMem 对"用户到底想干什么"的理解就越准。**

### 3.5 纯指令系统的上限 vs AI 的上限

这是一个必须要诚实承认的问题：

```
纯指令系统（模块化后）：
  ─ 做一件事 100% 正确
  ─ 毫秒级响应
  ─ 零成本
  ─ 但上限 = 你写了多少模块

AI 大模型：
  ─ 什么事都能试一下
  ─ 但可能出错、可能幻觉
  ─ 每次花几分钱
  ─ 上限 ≈ 整个互联网的知识

两个不冲突：
  用户的需求 = 日常固定操作(占80%) + 偶尔的新鲜事(占20%)
  纯指令覆盖那 80%，AI 覆盖那 20%
  随着时间推移，20% 里又有一部分变成固定操作 → 沉淀到纯指令
  → 80% 圈越来越大，20% 圈越来越小
```

## 四、研究问题一：模块越多越聪明还是越笨重？

### 4.1 先定义"聪明"和"笨重"

| 概念 | 定义 |
|------|------|
| **聪明** | 执行同样的任务，用的步骤更少、准确率更高、推荐更准 |
| **笨重** | 系统越来越卡、启动越来越慢、响应越来越迟钝 |

### 4.2 模块数量对"聪明"的影响

```
模块量级    对"聪明"的影响
───────────────────────────────────────────────
10 个      基准。每个模块都认识，但推荐能力弱
50 个      推荐开始有价值。"你上次截图后经常接压缩"
100 个     组合推荐变准。"电商客户常用：日报+库存查询+发群"
500 个     冷门场景也能覆盖。"这个从没见过的需求...记忆里 3 个相似案例"
∞         趋向"经验上限"——见过的都认识，没见过的不瞎猜
```

**越多越聪明，但有上限。** 不是线性增长的，到一定量级后接近饱和。

### 4.3 但模块再聪明也比不上 AI

这是必须诚实面对的：

```
纯指令系统（1000 个模块）：
  能做的事：1000 种固定操作
  没见过的需求："没有这个模块"→拒绝
  学习新能力：你要写一个新模块
  上限天花板：你写了多少模块就是多少

AI 大模型：
  能做的事：理论上任何语言能描述的事
  没见过的需求：尝试理解→可能对可能错
  学习新能力：描述给它听就行
  知识面：接近整个互联网

所以：纯指令不是去跟 AI 比"聪明"。
纯指令是去填补"AI 做不好但你又天天在做"的那些事。
              ↑
        这是两个赛道的产品
```

```
大模型 = 十万个为什么，什么都能聊两句
你的系统 = 操作手册，只写教过它的东西，写上去的就一定对

谁更好取决于你想要什么。
```

### 4.4 模块数量对"笨重"的影响

这才是关键问题。分析分三层：

**第一层：路由查找（完全没问题）**

```
10 个模块：   查字典，O(1)
100 个模块：  查字典，O(1)
1000 个模块： 查字典，O(1)
10000 个模块：查字典，O(1)

只要用哈希表（Python dict），模块数量对路由速度的影响 = 0。
```

**第二层：NLU 意图匹配（轻微影响）**

```
10 个意图：    TF-IDF 匹配，< 1ms
100 个意图：   TF-IDF 匹配，~3ms
1000 个意图：  TF-IDF 匹配，~30ms
10000 个意图： TF-IDF 匹配，可能 200ms+

需要优化的点：
  - 先按标签过滤（只匹配当前上下文相关的标签下的意图）
  - 缓存高频意图的向量
  - 200ms 对毫秒级仍是可接受范围
```

结论：**有影响，但可控，不需要大模型。**

**第三层：CogniMem 检索（影响最小）**

```
CogniMem 存储的三元组数量跟"模块数"无关，跟"执行次数"有关。
100 个模块 × 每个执行 1000 次 = 10 万条三元组

SQLite 查询 10 万条带索引的数据 → 仍然是 < 10ms
PostgreSQL 查询 100 万条 → 也是 < 50ms

影响几乎为 0。数据库就是干这个的。
```

### 4.5 综合结论

```
模块数量    路由速度    NLU 速度    检索速度    整体体感
────────────────────────────────────────────────────────
10          < 1ms      < 1ms       < 5ms      ⚡
50          < 1ms      ~1ms        < 10ms     ⚡
100         < 1ms      ~3ms        < 10ms     ⚡
500         < 1ms      ~15ms       < 20ms     ⚡
1000        < 1ms      ~30ms       < 30ms     ⚡ (仍然毫秒级)
```

结论：**不会笨重。路由是 O(1)，检索是 O(log n)，唯一线性增长的是 NLU 匹配，但到 1000 个模块也才 30ms。**

更聪明 + 不笨重 = **可行**。只是聪明的上限比不上大模型，但也不需要比。

## 五、研究问题二：模块越多出错修复越难？

### 5.1 模块之间的依赖关系是核心变量

这是需要认真分析的问题。

```
模块数量    依赖复杂度    出错影响面
────────────────────────────────────────────
10 个     几乎没有      一个模块坏了，就它自己不能用
50 个     开始出现 A→B   B 坏了，依赖 B 的 C 也受影响
100 个    网络状依赖     一个模块改动可能波及 10+ 个模块
500+ 个   需要治理       没有依赖管理会真的变成"牵一发动全身"
```

**但这是"写烂了"的情况。如果从一开始就控制好了，完全不一样。**

### 5.2 依赖爆炸只在一种情况下发生

不是模块多了就爆炸，是**模块之间乱依赖才爆炸**。

```
❌ 坏的设计：
  compress.py 依赖 screenshot.py（为什么截图模块会依赖压缩模块？）
  → 截图改了 → 压缩崩了 → 迷惑

✅ 好的设计：
  每个模块零依赖，或只依赖系统命令、标准库
  screenshot.py → 只调 screencapture
  compress.py   → 只调 zip
  它们之间没有任何代码级的依赖关系
```

### 5.3 两个核心约束（必须从第一天钉死）

```
约束一：模块之间不能互相 import
──────────────────────────────
  screenshot.py 不能 import compress.py
  compress.py 不能 import timer.py
  → 所有模块是"平铺的邻居"，不是"嵌套的家庭"

约束二：模块只能通过"组合"来协作
──────────────────────────────
  用户拖拽：截图 → 压缩 → 发邮件
                 ↑
          这是"使用层面的组合"，不是"代码层面的依赖"
          截图坏了 → 截图不能用了，但不影响压缩和发邮件
```

### 5.4 在这样的约束下，模块越多修复越难吗？

```
模块 100 个，全是平铺的、独立的：
  ─ 模块 A 坏了 → 只修 A，修完单测通过就完事
  ─ 不影响 B、C、D、E
  ─ 修复复杂度 = O(1)，跟模块总数无关
  ─ 新人加入，理解模块 A 只需要读 1 个文件，不需要读关联的 10 个文件

结论：修复难度是常数级，不随模块数量增长。
```

### 5.5 进一步：CogniMem 让修复更简单

CogniMem 在这里发挥的是"反面价值"——不是让它变复杂，是让它变简单：

```
场景：compress 模块报错了

没有 CogniMem：
  你看到报错 → 手动排查 → 发现是路径问题 → 修复
  下次同样报错 → 又手动排查一次

有 CogniMem：
  compress 报错 → 自动写入记忆
  "compress 上次报错：路径不存在 → 解决方案：检查输入路径"
  下次报错时系统自动调取历史记忆
  直接显示："这个错误出现了 7 次，上次原因是路径参数为空"
  → 排查时间从 15 分钟降到 10 秒
```

**而且 AI 模式下的错误排查更快：**

```
用户通过 AI 执行任务时 AI 报错了
CogniMem 自动匹配历史记录：
  "这个报错跟 3 天前客户 B 的报错 92% 相似"
  "上次解决方案：API token 过期，刷新后解决"
  → AI 下次重试时自动带上新的 token
  → 用户无感，错误已经自愈了
```

### 5.6 综合结论

| 场景 | 修复难度 | 原因 |
|------|---------|------|
| 独立模块（零依赖） | 恒定 O(1) | 修一个就是修一个 |
| 互相依赖的模块 | 线性增长 O(n) | 修一个可能影响一片 |
| 有 CogniMem 辅助 | 递减趋势 | 踩过的坑自动记录，越修越快 |
| AI+自愈 | 趋向零感 | 常见错误自动匹配解决方案并重试 |

**结论：如果坚持"模块零依赖"的纪律，模块越多不会导致修复越难。相反，配合 CogniMem，越修越快。** 但如果乱写依赖，到 100 个模块以后谁都救不了。

所以这个问题的答案**取决于纪律，不取决于技术**。

## 六、研究问题三：如何做安全锁防剽窃复制？

### 6.1 先认清一个事实

```
核心问题：你的东西到底什么值钱？

代码本身？
  防不住。Python 是明文，编译后的 .pyc 也能反编译。
  Docker 镜像也能被 pull 出来。
  → 靠"加密代码"防剽窃 = 防君子不防小人。

那什么值钱？什么才真的防得住？
```

### 6.2 真正值钱的东西恰恰复制不走

| 资产 | 能不能复制 | 为什么 |
|------|-----------|--------|
| 模块代码 | ✅ 能复制 | 明文 Python，拿到就能用 |
| **CogniMem 积累的记忆数据** | ❌ **复制不走** | 每个客户的执行记录是独一无二的，从零培养要时间 |
| **模块之间的组合模式** | ❌ **复制不走** | 你跟客户磨合出来的"最佳流程"，不是代码能表达的 |
| **故障知识库** | ❌ **复制不走** | 踩过的坑要重新踩一遍才能积累到相同深度 |
| **解决方案库** | ❌ **复制不走** | 针对客户具体环境的"修复方案"，换环境不通用 |
| **AI 行为历史积累** | ❌ **复制不走** | AI 为客户处理过的任务类型、频次、结果——这些数据定义了"这个客户特有的需求画像" |
| **客户信任 + 服务响应** | ❌ **复制不走** | 这跟技术无关，纯粹的长期关系 |

**最值钱的东西，不是代码，是时间积累出来的数据。**

### 6.3 技术层面的防剽窃手段

以下按强度排列，你可以选几个组合：

**方案 A：模块签名校验（最轻量，基础防护）**

```python
# 每次加载模块时校验签名
import hmac, hashlib

SECRET = os.environ.get("EXECUTOR_SECRET", "")

def verify_module(mod_path: Path) -> bool:
    """校验模块文件的 HMAC 签名，防篡改"""
    with open(mod_path, "rb") as f:
        content = f.read()
    
    # 签名的最后 32 字节
    expected_sig = content[-32:]
    actual_sig = hmac.new(
        SECRET.encode(), content[:-32], hashlib.sha256
    ).digest()
    
    return hmac.compare_digest(expected_sig, actual_sig)
```

优点：最简单。  
缺点：防不了复制——人家连你的 SECRET 一起复制走就没用了。

**方案 B：CogniMem 绑定许可（中等强度）**

```
每个部署实例有一个唯一的 Device ID（基于硬件信息生成）

CogniMem 存储的"记忆数据"与 Device ID 加密绑定。
即使模块代码被复制走：
  ├── 换了机器 → Device ID 不同
  ├── CogniMem 拒绝加载记忆数据
  └── 剽窃者拿到了模块，但没有积累的执行记忆
```

适合场景：客户端的部署。

**方案 C：核心模块远程验证（较强防护）**

```
关键模块（如 NLU 意图映射器、CogniMem 检索引擎）
不在本地部署，而是放在你自己的服务器上。
本地部署的是"执行器"，向你的服务器验证身份后才能拿到核心能力。

优点：核心资产永远在你的服务器上。
缺点：需要保持网络连接。不过你的方案本来就需要联网。
```

**方案 D：记忆数据加密存储（终极方案）**

```
所有 CogniMem 存储的三元组、版本链、故障知识库，
在写入磁盘时全部用 AES-256-GCM 加密。

密钥来源：
  ├── 硬件绑定（TPM 芯片 / 网卡 MAC / CPU 序列号）
  ├── 或者用户输入的密码
  └── 或者远程服务器下发的许可

即使硬盘被拔走：得到一堆二进制乱码。
即使代码被复制走：没有密钥读不了记忆数据。
```

### 6.4 推荐组合（轻量但实用）

```
第一层：模块签名校验
  ─ 防篡改，确保你写的模块没有被别人改过

第二层：CogniMem 记忆绑定
  ─ 每个客户的记忆数据绑定到他们的部署实例
  ─ 模块代码可以拷，但记忆数据拷不走、换不了机器用

第三层：核心引擎不在模块里
  ─ 路由引擎 + NLU 映射 + 记忆检索做成独立的二进制文件或加密包
  ─ 模块 .py 文件是公开的，但"执行框架"是受保护的

第四层：关键是"服务"
  ─ API 变化你要跟着适配
  ─ 客户环境你熟悉
  ─ 故障排除你最快
  ─ 这是法律和技术都防不住的东西——但你靠服务本身建了护城河
```

### 6.5 综合结论

```
技术上能防的：
  ✅ 模块签名（防篡改，不防盗版）
  ✅ 记忆加密 + 机器绑定（防拷贝后直接使用）
  ✅ 核心引擎远程验证（被盗的模块缺核心能力）

技术上限：
  ❌ 绝对防不住有耐心的破解者（任何软件都做不到）
  
真正的护城河不是技术：
  ✅ 你的记忆数据（时间积累出来的）
  ✅ 你的服务响应速度（大厂做不到）
  ✅ 你对每个客户环境的了解（别人要从零学）
```

**结论：能做安全锁，但不能依赖它。真正的"锁"是你的数据积累速度——剽窃者拿到代码的那一刻，你的系统已经又跑了一个月、又积累了新知识。他一直追不上。**

## 八、五个要研究的关键问题

> 以下是我认为在你做决定之前值得深入研究的问题。

### 8.1 沉淀阈值怎么定

```
最关键的问题：什么时候该把一个 AI 任务做成模块？

阈值太松：
  用户让 AI 干了两次就想做模块 → 结果这个操作再也不用了
  → 白花了写模块的时间

阈值太紧：
  用户每天都让 AI 干同一件事 → 一直花 AI 的钱
  → 明明 30 分钟就能做成模块省掉

要研究：
  ─ 基于"频次 + 趋势"的阈值算法
  ─ 比如：3 天内出现 3 次以上 → 建议沉淀
  ─ 或者：第一次出现后 7 天内又出现 → 建议沉淀
  ─ 这个需要实验数据来调
```

### 8.2 AI 执行结果怎么自动转化为模块骨架

```
用户让 AI "爬京东商品评价" → AI 跑了个 Python 脚本

如果要把这个沉淀成模块：
  ─ 是直接保存 AI 生成的脚本？
  ─ 还是需要人工重写一遍？
  ─ 能不能让 AI 自动生成一个"模块模板"，你只需要微调？

要研究：
  ─ AI 生成的代码作为"模块草稿"的可行性
  ─ 草稿→正式模块的校验流程
  ─ 安全性（AI 生成的代码能不能直接跑？）
```

### 8.3 组合指令的存储与检索

```
用户拖了一个"截图→压缩→发邮件"的流水线。
这应该在 CogniMem 里怎么存？

两种思路：
  A. 存为一条"组合三元组"：组合_ID, 包含模块, [截图, 压缩, 发邮件]
  B. 存为多条"相邻关系"：截图→压缩、压缩→发邮件

哪个检索效率更高？哪个更能推荐出有用的组合？
需要实验验证。
```

### 8.4 遗忘策略在模块场景下的调优

```
CogniMem 的艾宾浩斯遗忘参数（7-60 天半衰期）是为"认知记忆"设计的。

但在执行系统场景下：
  ─ 故障记录：应该保留更久（踩过的坑不能忘）
  ─ 用户偏好：可能变化（用户换工作流了）
  ─ 执行频率：大促期间频次暴增，平时很低
  ─ AI 任务记录：是一次性的还是有长期价值的？

需要为"执行数据"设计一套独立的衰减参数。
```

### 8.5 NLU 映射的冷启动问题

```
TF-IDF 需要种子样本，第一个模块写完后，只有 5-10 条例句。
用户前几次用自然语言触发，识别率可能不高。

但有了 AI 模式后，冷启动有了新解法：
  ─ 初期没有模块 → 全部走 AI
  ─ AI 处理了 N 次后 → CogniMem 积累了用户的表达方式
  ─ 沉淀成模块时 → 种子样本已经有了，不需要手动写

要研究：
  ─ AI 积累的表达方式能否自然转化为 NLU 样本？
  ─ 转化后的准确率比手动写的差多少？
```
